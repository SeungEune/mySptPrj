# UI Rules

`mySptPrj`의 Thymeleaf / CSS / JS 기반 화면 작업 규칙.

## 1. 기본 원칙

### 공통 우선
- 새 화면 또는 수정 작업 전, 기존 공통 스타일과 유사 화면을 먼저 확인한다.
- 버튼, 카드, 타이포, spacing은 기존 공통 규칙을 우선 재사용한다.
- 현재 디자인 시스템과 이질적인 페이지를 단독으로 만들지 않는다.

### 최소 변경
- 문제 해결 범위만 수정한다.
- 디자인 수정과 구조 리팩터링을 한 번에 섞지 않는다.

### 일관성 유지
- 같은 유형의 화면은 가능한 한 같은 UI 패턴을 따른다.
- 에러 페이지/목록/상세/모달 간의 톤과 구조를 통일한다.

### 현실 우선
- reference 문서보다 현재 프로젝트의 실제 클래스/레이아웃/자산 구조를 우선 근거로 삼는다.
- 새로운 디자인 체계를 즉시 강제하지 않고, 현재 구조 안에서 개선한다.

## 2. CSS 구조 규칙

### 공통 파일 역할
- `static/css/common.css`
  - 디자인 토큰(`--spt-*`)
  - 공통 레이아웃
  - 타이포 유틸리티
  - spacing / display 유틸
- `static/css/components.css`
  - 버튼
  - 배지
  - 재사용 가능한 공통 컴포넌트
- `static/css/cmm/`
  - 헤더/푸터/로그인/공통 화면 스타일

### 화면 전용 파일 역할
- 특정 화면 전용 스타일은 `static/css/<module>/...` 아래에 둔다.
- 시스템 화면은 `static/css/system/...`
- 메인 화면은 `static/css/main/...`
- 추가 스타일이 필요하면 가능한 한 **같은 도메인 또는 같은 화면 맥락의 CSS 파일**을 별도로 만들어 작업한다.

### 공통 CSS 수정 원칙
- 먼저 `common.css`, `components.css`, `cmm/` 공통 CSS에서 재사용 가능한 규칙이 있는지 확인한다.
- 공통 CSS는 여러 화면에서 함께 써야 하는 규칙이 명확할 때만 수정한다.
- 단일 화면 대응이나 일회성 요구사항 때문에 공통 CSS를 오염시키지 않는다.
- 공통 CSS 수정 전에는 영향 범위를 먼저 확인하고, 가능하면 화면 전용 CSS로 해결 가능한지 검토한다.

### 금지
- 없는 CSS 파일을 참조하지 않는다.
- 색상/간격 값을 하드코딩으로 남발하지 않는다.
- 같은 역할의 스타일을 여러 파일에 중복 정의하지 않는다.
- 단일 화면 수정 때문에 `common.css`, `components.css`, `cmm/` 공통 CSS를 직접 수정하는 것을 기본 해법으로 삼지 않는다.

## 3. 스타일 작성 원칙

### 토큰 사용
- 가능하면 `var(--spt-*)` 토큰을 사용한다.
- 배경, 텍스트, 보더, 간격은 기존 변수 체계를 우선 따른다.
- reference의 토큰 체계는 참고자료일 뿐, 현재 프로젝트에는 `--spt-*`가 기준이다.

### 버튼 사용
- 기본 버튼은 아래 클래스 체계를 우선 사용한다.
  - `primary-button`
  - `secondary-button`
  - `outline-button`
  - `tertiary-button`
- 버튼 크기는 기존 `lg`, `md`, `sm` 규칙을 따른다.
- 버튼 의미는 아래처럼 유지한다.
  - 주요 액션: 등록, 저장, 확인
  - 보조 액션: 목록, 취소, 닫기
  - 위험 액션: 삭제, 초기화, 되돌리기

### 타이포 사용
- 제목/본문 스타일은 기존 유틸리티를 우선 사용한다.
  - `txt-head-lg`, `txt-head-md`, `txt-head-sm`, `txt-head-xs`
  - `txt-body-md`, `txt-body-sm`, `txt-body-xs`

## 4. 템플릿 구조 규칙

### 레이아웃 우선
- 공통 헤더/푸터/메타/스크립트는 기존 fragment를 우선 사용한다.
- 메인 계열 화면은 `cmm/layout/mainLayout.html` 기반 구조를 우선 고려한다.

### fragment 재사용
- 아래 공통 fragment를 먼저 확인한다.
  - `cmm/header.html`
  - `cmm/footer.html`
  - `cmm/meta.html`
  - `cmm/script.html`
  - `cmm/loading.html`

### 에러 페이지 규칙
- 403/404/500은 같은 톤과 구조를 유지한다.
- 현재 사용 중인 로고와 공통 스타일만 참조한다.
- 존재하지 않는 예전 자산(`funLogo`, `error.css` 등)을 다시 도입하지 않는다.

## 5. 마크업 구조 및 접근성 규칙

### 기본 원칙
- 클래스 체계는 현재 프로젝트 기준을 따르되, DOM 구조는 명확하고 예측 가능하게 유지한다.
- 버튼, 링크, 탭, 모달, 테이블은 역할이 드러나는 구조를 사용한다.

### 버튼/링크
- 버튼 내부 텍스트는 가능하면 명확한 텍스트 노드 또는 `<span>`으로 감싼다.
- 아이콘 버튼은 텍스트 또는 접근성 라벨을 함께 고려한다.

### 테이블
- 데이터 테이블은 가능하면 `caption` 또는 대체 설명을 고려한다.
- 화면에 보이지 않는 설명이 필요하면 `sr-only` 패턴을 사용한다.
- 빈 상태 문구는 `조회 결과가 없습니다.`처럼 짧고 일관되게 유지한다.

### 폼
- 필수 입력 여부는 label, th, 설명 문구 중 하나 이상으로 명확히 드러나야 한다.
- 도움말/단위/제약 조건은 입력 요소 가까이에 둔다.

### 탭/모달
- 탭/모달 구조 변경 시 활성 상태 클래스와 JS selector 영향을 함께 확인한다.
- 접근성 속성은 현재 구조를 해치지 않는 범위에서 점진적으로 보강한다.

## 6. JS 연계 규칙

- 템플릿 수정 시 연결된 JS 파일이 있는지 함께 확인한다.
- DOM 구조 변경 시 selector 영향 범위를 검토한다.
- JS에서 의존하는 id/class를 함부로 바꾸지 않는다.
- 탭, 모달, 검색 폼처럼 동작이 있는 영역은 마크업 구조 변경 전에 관련 이벤트 바인딩을 먼저 확인한다.

## 7. 문구 규칙

### 사용자 메시지 톤
- 짧고 명확하게 쓴다.
- 문제 상황에서는 원인보다 다음 행동을 안내한다.
- 제품 전반 톤을 벗어나는 과장된 문구를 쓰지 않는다.
- 내부 구현 용어를 그대로 노출하지 않는다.

### 행동 중심 문구
- 버튼/링크/안내 문구는 사용자가 무엇을 할 수 있는지 드러나게 쓴다.
- 상태 문구는 현재 상태를 짧게 설명하고, 필요하면 다음 행동을 함께 제시한다.

### 예시
- 좋은 예: `요청하신 페이지를 찾을 수 없습니다.`
- 좋은 예: `메인으로 이동하거나 관리자에게 문의해 주세요.`
- 좋은 예: `저장하시겠습니까?`
- 피할 예: 지나치게 장황한 기술 설명, 내부 구현 용어 노출

## 8. 수정 전 확인 항목

- 현재 화면 템플릿 위치를 찾았는가?
- 연결된 CSS / JS 파일을 확인했는가?
- 유사 화면과 패턴이 일치하는가?
- 공통 스타일 재사용이 가능한가?
- 현재 클래스 체계와 충돌하는 새 규칙을 도입하려는 것은 아닌가?

## 9. 수정 후 확인 항목

- 깨진 정적 리소스 참조가 없는가?
- 버튼, 텍스트, 간격 스타일이 기존 시스템과 어울리는가?
- 관련 유사 화면도 함께 점검했는가?
- 마크업 변경이 JS 동작에 영향을 주지 않는가?
- 변경 이유와 검증 포인트를 설명할 수 있는가?

## 10. 관련 패턴 문서

- 컴포넌트 DOM 구조와 현재 클래스 체계 기준 예시는 `docs/ui-component-patterns.md`를 참고한다.
- 이 문서는 규칙 문서이고, 패턴 예시는 별도 문서로 유지한다.

## 11. 예외 규칙

- 급한 복구 상황에서는 템플릿 내부 `<style>`을 임시로 사용할 수 있다.
- 단, 장기 유지 대상이라면 이후 전용 CSS 파일 또는 적절한 공통 위치로 정리해야 한다.
- 예외를 사용했으면 작업 요약에 반드시 남긴다.
- reference 문서의 패턴을 실험적으로 일부 적용할 경우에도, 현재 클래스 체계와 충돌하지 않는지 먼저 확인한다.
